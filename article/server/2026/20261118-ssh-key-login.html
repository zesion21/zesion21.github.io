SSH 密钥登录配置与排错：一次 Debian 免密登录的真实记录

阿琛2026/11/18大约 11 分钟Serversshlinuxdebianwindows

从密码登录改成 SSH 密钥登录，核心只有三步：客户端生成密钥对、把公钥放到服务器、测试登录。但真正常卡住人的往往不是这三步命令，而是服务端没有接受公钥和服务端目录权限不符合 sshd 要求这两个坑。本文按一次实际配置过程整理完整操作，并把两个问题的现场日志、原因和修复命令一并记录下来，环境是 WSL 中的 Ubuntu 客户端连接 Debian 12 服务器。

一、密钥登录到底做了什么

SSH 公钥认证使用一对密钥：

  • 私钥：留在客户端，不能上传服务器，也不能发给别人。
  • 公钥：可以公开，追加到服务器的 ~/.ssh/authorized_keys。

登录时客户端用私钥对服务端给出的挑战做签名，服务端用 authorized_keys 里对应的公钥验签，通过即可登录，私钥本身不会通过网络传输。

另外，服务端 sshd 在认证前会检查用户主目录和密钥文件的属主、权限，这就是本文问题二的来源。

二、Windows 客户端：生成密钥并上传

1. 生成密钥对

在 Windows PowerShell 中执行：

ssh-keygen -t ed25519 -C "windows-ssh"
  • -t ed25519：指定 Ed25519 算法，密钥短、签名快，当前 OpenSSH 生成密钥的默认类型也是 Ed25519。
  • -C：给密钥加注释，方便在服务器上分辨来源。

回车确认保存路径，再决定是否设置私钥密码。设置密码更安全，但每次使用都要输入；不设置则使用起来最省事，后续也可以用 ssh-agent 缓存。

默认会在 C:\Users\你的用户名\.ssh\ 下生成两个文件：

id_ed25519       # 私钥，留在本机
id_ed25519.pub   # 公钥，放到服务器

2. 把公钥追加到服务器

推荐直接在 PowerShell 里用管道完成：

Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub" | ssh root@192.168.1.100 "umask 077; mkdir -p ~/.ssh; cat >> ~/.ssh/authorized_keys"

第一次执行需要输入服务器登录密码。命令里的 umask 077 保证新建文件只有属主可读写（等价于 600），避免 authorized_keys 权限过宽。换成普通用户登录时，把 root 改成对应用户名即可。

也可以手动添加：先在客户端 cat ~/.ssh/id_ed25519.pub 复制整行内容，登录服务器后执行：

mkdir -p ~/.ssh
chmod 700 ~/.ssh
nano ~/.ssh/authorized_keys   # 粘贴公钥
chmod 600 ~/.ssh/authorized_keys

3. 测试登录

ssh -i "$env:USERPROFILE\.ssh\id_ed25519" root@192.168.1.100

如果仍然要求输入服务器密码，不要急着改服务器配置，先用 ssh -v 看客户端发出了哪个公钥、服务端是否接受：

ssh -v root@192.168.1.100

三、Linux 客户端：三条命令

本次实际环境是 WSL 中的 Ubuntu 客户端（OpenSSH 10.2p1）连接 Debian 12 服务器（OpenSSH 9.2p1，192.168.10.13，登录用户 tyxk13）。这台服务器也作为服务端出现在之前的 使用 WireGuard 实现局域网组建 中。客户端是 Linux 时流程更短：

# 1. 生成密钥；如果已有可用密钥，不要覆盖，直接复用
ssh-keygen -t ed25519

# 2. 上传公钥，输入一次服务器密码
ssh-copy-id -i ~/.ssh/id_ed25519.pub tyxk13@192.168.10.13

# 3. 测试登录
ssh tyxk13@192.168.10.13

ssh-copy-id 会自动创建 ~/.ssh 并把公钥追加到 authorized_keys（文件已存在则追加，不会覆盖其他公钥）。它依赖密码登录来完成这一步；如果服务端已经禁用了密码认证，就只能通过现有管理员权限手动安装公钥。

需要指定端口或其他 SSH 选项时，可以加 -p 2222、-o 等参数透传，但更推荐直接写进 ~/.ssh/config。

四、配置 SSH 别名

服务器多了以后，记用户名、端口和密钥路径很麻烦，可以统一写进 ~/.ssh/config。Windows 下是 C:\Users\你的用户名\.ssh\config，Linux/macOS 下是 ~/.ssh/config：

Host myserver
    HostName 192.168.10.13
    User tyxk13
    Port 22
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes

之后直接 ssh myserver 即可。IdentitiesOnly yes 限制客户端只使用这里指定的密钥，避免 ssh-agent 里的其他密钥被先尝试（服务端 MaxAuthTries 默认为 6，密钥太多时可能还没轮到正确的就被断开）。

多台服务器就写多个 Host 块，需要不同密钥时各自指定 IdentityFile。VS Code Remote-SSH、JetBrains 系列 IDE 也会读取这份配置。Linux 上建议顺手收紧权限：chmod 600 ~/.ssh/config。

五、问题一：公钥被拒绝，登录退回密码

现象

客户端执行 ssh -v tyxk13@192.168.10.13，网络和握手阶段全部正常，但认证阶段出现：

debug1: Authentications that can continue: publickey,password
debug1: Next authentication method: publickey
debug1: Offering public key: /home/zechen/.ssh/id_ed25519 ED25519 SHA256:ALjkLFEkqI3LYb2gDKtdTUjcbrSFaSJZb/c4sAAuBlA
debug1: Authentications that can continue: publickey,password
debug1: Next authentication method: password

日志怎么读

  • Connection established、Server host key 与 known_hosts 匹配：网络、端口和主机密钥都正常。
  • server-sig-algs 中包含 ssh-ed25519：服务端支持这种密钥算法。
  • Offering public key:：客户端确实把 id_ed25519 公钥发给了服务端。
  • 之后服务端再次返回 Authentications that can continue: publickey,password，并让客户端改用 password：说明服务端没有接受这个公钥。

所以“提示输入密码”并不代表密钥不存在或算法不对，而是服务端拒绝了这把公钥后，客户端按顺序回退到了密码认证。

原因

公钥没有写进当前登录用户的 authorized_keys，或者写入位置、权限不对。常见情况：

  • 公钥加到了 root 的 authorized_keys，但当前登录的是 tyxk13；
  • ~/.ssh/authorized_keys 不存在，或原有内容被覆盖；
  • .ssh 目录、authorized_keys 的权限不符合 sshd 要求（见问题二）。

处理

在客户端重新安装一次公钥：

ssh-copy-id -i ~/.ssh/id_ed25519.pub tyxk13@192.168.10.13

然后指定密钥测试，确认只使用这一把密钥：

ssh -i ~/.ssh/id_ed25519 -o IdentitiesOnly=yes tyxk13@192.168.10.13

如果仍然要求密码，继续往下排查。

核对两端是不是同一把公钥

客户端查看公钥指纹：

ssh-keygen -lf ~/.ssh/id_ed25519.pub

服务端查看已授权公钥的指纹：

ssh-keygen -lf ~/.ssh/authorized_keys

两边输出应包含相同的指纹。本次两端一致，指纹为：

SHA256:ALjkLFEkqI3LYb2gDKtdTUjcbrSFaSJZb/c4sAAuBlA

指纹一致但登录失败，问题就落在服务端权限上；指纹不一致则说明公钥根本没装到正确用户下。

查看服务端日志

在服务端实时查看认证日志：

sudo journalctl -u ssh -f

保持这个终端打开，客户端再重试一次 ssh -v，服务端日志通常能直接给出拒绝原因。本次正是通过这一步拿到了下一个问题的关键报错。

到这里可以确认：日志中没有算法不匹配、网络或密钥格式问题，因此不需要修改 sshd_config，也不需要重新生成密钥，问题只在“公钥怎么装、权限对不对”。

六、问题二：bad ownership or modes for directory /home/tyxk13

现象

服务端日志出现：

Authentication refused: bad ownership or modes for directory /home/tyxk13

原因：StrictModes

OpenSSH 的 StrictModes 默认为 yes，sshd 在接受登录前会检查用户主目录及相关文件的属主和权限。只要主目录或 ~/.ssh 被组或其他用户写入，或者属主不是该用户（也不是 root），认证就会被拒绝。

这样设计的原因很直接：如果别人能写你的 ~/.ssh/authorized_keys，就等于别人能把公钥塞进来接管你的账号。

实际环境里最常见的触发场景：

  • 为了文件共享把主目录设置成 775 或 777；
  • 主目录是 Samba/NFS 共享目录，权限被共享配置放宽；
  • 曾用 root 执行过 chown -R，把主目录属主改错；
  • 用户目录刚创建，属主和权限还没配好。

排查

在服务端依次检查三处权限：

ls -ld /home/tyxk13
ls -ld /home/tyxk13/.ssh
ls -l /home/tyxk13/.ssh/authorized_keys

要看整条路径上每一级目录的属主和权限，用 namei 更直观：

namei -l /home/tyxk13/.ssh/authorized_keys

本次问题就出在 /home/tyxk13 这个主目录本身：权限过宽或属主不正确，sshd 在检查第一层目录时就拒绝了。

修复

在 Debian 服务端执行：

# 主目录：属主必须是该用户，且不能被组或其他用户写入
sudo chown tyxk13:tyxk13 /home/tyxk13
sudo chmod 755 /home/tyxk13

# .ssh 目录和 authorized_keys
sudo chown -R tyxk13:tyxk13 /home/tyxk13/.ssh
sudo chmod 700 /home/tyxk13/.ssh
sudo chmod 600 /home/tyxk13/.ssh/authorized_keys

修复后的正常状态：

drwxr-xr-x tyxk13 tyxk13 /home/tyxk13
drwx------ tyxk13 tyxk13 /home/tyxk13/.ssh
-rw------- tyxk13 tyxk13 authorized_keys

主目录也可以按需要设成 750（同组用户可进入）或 700，前提是其他用户确实需要访问该目录时才放宽；关键是不能被组或其他用户写入。

验证

客户端重新连接：

ssh -i ~/.ssh/id_ed25519 tyxk13@192.168.10.13

能直接登录就说明公钥认证已经通过。修复权限不需要重启 sshd，也不需要重新生成密钥。

不要用关闭 StrictModes 来绕过

把 sshd_config 里的 StrictModes 改成 no 确实能让报错消失，但这等于允许别人修改你的 authorized_keys，风险远大于收益。正确做法是修好目录权限；如果问题确实来自 Samba 等共享目录，就调整共享目录结构或权限，而不是放宽 SSH 的检查。

七、可选加固：禁用密码登录

确认密钥登录完全可用后再做。操作时保持一个已经登录的 SSH 会话不要断开，用新连接验证成功后再退出旧会话，避免把自己锁在服务器外。

Ubuntu/Debian 上检查 /etc/ssh/sshd_config 以及 /etc/ssh/sshd_config.d/ 下的配置（存在同名配置时注意生效顺序）。确保最终生效值为：

PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no

然后校验并重载：

sudo sshd -t
sudo systemctl reload ssh

reload 会重新加载配置，不会断开已有会话，比 restart 更稳妥。不同发行版的服务名可能是 ssh 或 sshd；部分系统 sshd 不在 PATH 中，需要用 /usr/sbin/sshd -t。是否允许 root 直接登录还要看 PermitRootLogin 的配置。

八、多台服务器和多套密钥

一套密钥对可以复用：把同一个公钥分别追加到每台服务器的 ~/.ssh/authorized_keys，再用 ~/.ssh/config 配置不同别名。

ssh server1
ssh server2

如果不同环境需要不同密钥（例如生产、测试分开），在 config 里按 Host 指定各自的 IdentityFile 即可；配合 IdentitiesOnly yes，避免客户端把 agent 里的多把密钥挨个试一遍。

九、常见问题

Q：配置完为什么还要输入密码？

先区分是哪种密码：出现 Enter passphrase for key 是私钥密码；出现 tyxk13@192.168.10.13's password: 是服务器账号密码。后者说明公钥认证没有通过，用 ssh -v 看 Offering public key 之后服务端返回了什么。

Q：修改 authorized_keys 后要重启 sshd 吗？

不需要。authorized_keys 和权限在每次认证时读取，改完直接重新连接即可；只有修改 sshd_config 才需要 systemctl reload ssh。

Q：Permission denied (publickey) 怎么查？

按顺序检查：公钥是否装在当前用户下、两端指纹是否一致、主目录/.ssh/authorized_keys 属主与权限、服务端日志。

Q：公钥可以公开吗？

可以。公钥本来就是交给服务器验证用的，私钥才是必须保密的部分。私钥文件权限建议设置为 600。

Q：私钥密码每次都要输入怎么办？

用 ssh-agent 缓存。Linux/WSL 下执行 eval "$(ssh-agent -s)" 后 ssh-add ~/.ssh/id_ed25519；Windows 的 OpenSSH 客户端可启用 ssh-agent 服务后使用 ssh-add。

Q：主目录为什么不能设置成 777？

StrictModes 会认为其他用户能写主目录，也就能替换 authorized_keys，因此拒绝认证。需要共享文件时，把共享目录和家目录分开。

十、总结

整条链路可以记成五步：

  1. 客户端生成密钥对；
  2. 公钥追加到目标用户的 ~/.ssh/authorized_keys；
  3. 客户端用指定密钥测试登录；
  4. 写入 ~/.ssh/config 简化连接；
  5. 确认可用后再禁用密码认证。

本次两个问题的排查顺序也很固定：先 ssh -v 确认客户端做了什么，再核对两端公钥指纹，然后看服务端日志 journalctl -u ssh -f，最后检查 StrictModes 相关的目录权限。

一句话：密钥登录失败时，优先看服务端日志和目录权限，而不是反复重新生成密钥或修改 sshd 配置。
