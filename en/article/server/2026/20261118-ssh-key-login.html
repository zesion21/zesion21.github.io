SSH Key Login: Setup and Troubleshooting a Real Debian Passwordless Login

阿琛11/18/26About 8 minServersshlinuxdebianwindows

Switching from password login to SSH key login takes just three steps: generate a key pair on the client, put the public key on the server, and test the login. What actually trips people up is usually not these commands, but two pitfalls: the server does not accept the public key, and the server directory permissions do not satisfy sshd's requirements. This article walks through the full setup based on a real configuration session, and records the live logs, causes, and fix commands for both problems. The environment was an Ubuntu client in WSL connecting to a Debian 12 server.

1. What key-based login actually does

SSH public key authentication uses a key pair:

  • Private key: stays on the client. It must not be uploaded to the server or shared with anyone.
  • Public key: can be public. It is appended to ~/.ssh/authorized_keys on the server.

When logging in, the client signs a challenge from the server with the private key, and the server verifies the signature with the matching public key in authorized_keys. Once verified, the login succeeds. The private key itself never travels over the network.

In addition, before authentication the server's sshd checks the ownership and permissions of the user's home directory and key files. That is where the second problem in this article comes from.

2. Windows client: generate a key and upload it

2.1 Generate a key pair

Run this in Windows PowerShell:

ssh-keygen -t ed25519 -C "windows-ssh"
  • -t ed25519: use the Ed25519 algorithm. Keys are short and signatures are fast; it is also the default key type for current OpenSSH.
  • -C: add a comment to the key so it is easy to identify where it came from when listed on the server.

Press Enter to confirm the default path, then decide whether to set a private key passphrase. A passphrase is more secure but requires input on every use; leaving it empty is the most convenient. Later you can also cache it with ssh-agent.

By default, two files are created under C:\Users\your-username\.ssh\:

id_ed25519       # private key, stays on this machine
id_ed25519.pub   # public key, goes to the server

2.2 Append the public key to the server

The recommended way is a PowerShell pipeline:

Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub" | ssh root@192.168.1.100 "umask 077; mkdir -p ~/.ssh; cat >> ~/.ssh/authorized_keys"

The first run asks for the server login password. umask 077 ensures new files are readable and writable only by their owner (equivalent to 600), preventing overly permissive authorized_keys permissions. If you log in as a regular user, replace root with that username.

You can also add it manually: run cat ~/.ssh/id_ed25519.pub on the client and copy the whole line. Then log in to the server and run:

mkdir -p ~/.ssh
chmod 700 ~/.ssh
nano ~/.ssh/authorized_keys   # paste the public key
chmod 600 ~/.ssh/authorized_keys

2.3 Test the login

ssh -i "$env:USERPROFILE\.ssh\id_ed25519" root@192.168.1.100

If the server still asks for the account password, do not rush to change server configuration. First use ssh -v to see which public key the client offers and whether the server accepts it:

ssh -v root@192.168.1.100

3. Linux client: three commands

The actual environment in this session was an Ubuntu client in WSL (OpenSSH 10.2p1) connecting to a Debian 12 server (OpenSSH 9.2p1, 192.168.10.13, login user tyxk13). This server also appears as the server side in Building a Local Area Network with WireGuard. When the client is Linux, the process is shorter:

# 1. Generate a key; if you already have a usable key, reuse it instead of overwriting
ssh-keygen -t ed25519

# 2. Upload the public key, entering the server password once
ssh-copy-id -i ~/.ssh/id_ed25519.pub tyxk13@192.168.10.13

# 3. Test the login
ssh tyxk13@192.168.10.13

ssh-copy-id automatically creates ~/.ssh and appends the public key to authorized_keys (it appends if the file exists and does not overwrite other keys). It relies on password login to do this; if the server has already disabled password authentication, the key must be installed manually with existing administrator access.

To specify a port or other SSH options, pass them through with -p 2222, -o, and so on. Writing them into ~/.ssh/config is usually cleaner.

4. Configure SSH aliases

Once there are several servers, remembering usernames, ports, and key paths becomes tedious. Put them in ~/.ssh/config. On Windows this is C:\Users\your-username\.ssh\config; on Linux/macOS it is ~/.ssh/config:

Host myserver
    HostName 192.168.10.13
    User tyxk13
    Port 22
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes

After that, just run ssh myserver. IdentitiesOnly yes restricts the client to only the key specified here, preventing other keys in ssh-agent from being tried first (the server's default MaxAuthTries is 6, so with too many keys the correct one may never be reached before the connection is dropped).

For multiple servers, add multiple Host blocks, and specify a different IdentityFile when a different key is needed. VS Code Remote-SSH and JetBrains IDEs also read this configuration. On Linux, tighten the file permissions as well: chmod 600 ~/.ssh/config.

5. Problem 1: the public key is rejected and login falls back to password

5.1 Symptom

Running ssh -v tyxk13@192.168.10.13 on the client, everything in the network and handshake phases looks fine, but the authentication phase shows:

debug1: Authentications that can continue: publickey,password
debug1: Next authentication method: publickey
debug1: Offering public key: /home/zechen/.ssh/id_ed25519 ED25519 SHA256:ALjkLFEkqI3LYb2gDKtdTUjcbrSFaSJZb/c4sAAuBlA
debug1: Authentications that can continue: publickey,password
debug1: Next authentication method: password

5.2 How to read the log

  • Connection established and a Server host key matching known_hosts: networking, port, and host key are all fine.
  • server-sig-algs includes ssh-ed25519: the server supports this key algorithm.
  • Offering public key:: the client really did send the id_ed25519 public key to the server.
  • Afterwards the server again returns Authentications that can continue: publickey,password and makes the client switch to password: the server did not accept this public key.

So "it asks for a password" does not mean the key is missing or the algorithm is wrong. The server rejected this key, and the client fell back to password authentication in order.

5.3 Cause

The public key was not written into the current login user's authorized_keys, or it was written to the wrong place or with wrong permissions. Common cases:

  • The key was added to root's authorized_keys, but the current login is tyxk13.
  • ~/.ssh/authorized_keys does not exist, or its previous content was overwritten.
  • The permissions of the .ssh directory or authorized_keys do not satisfy sshd (see problem 2).

5.4 Fix

Install the public key again from the client:

ssh-copy-id -i ~/.ssh/id_ed25519.pub tyxk13@192.168.10.13

Then test with the key explicitly, ensuring only this key is used:

ssh -i ~/.ssh/id_ed25519 -o IdentitiesOnly=yes tyxk13@192.168.10.13

If it still asks for a password, keep troubleshooting below.

5.5 Verify that both sides have the same public key

On the client, show the public key fingerprint:

ssh-keygen -lf ~/.ssh/id_ed25519.pub

On the server, show the fingerprints of authorized keys:

ssh-keygen -lf ~/.ssh/authorized_keys

Both outputs should contain the same fingerprint. In this session they matched:

SHA256:ALjkLFEkqI3LYb2gDKtdTUjcbrSFaSJZb/c4sAAuBlA

If the fingerprints match but login still fails, the problem lies in server-side permissions. If they differ, the public key was simply not installed for the right user.

5.6 Check the server log

Watch authentication logs on the server in real time:

sudo journalctl -u ssh -f

Keep that terminal open and retry ssh -v from the client. The server log usually gives the rejection reason directly. In this session, this is exactly how the key error for the next problem was found.

At this point we can confirm: there is no algorithm mismatch, network issue, or key format problem in the logs. So there is no need to modify sshd_config or regenerate the key pair; the problem is only about how the public key is installed and whether permissions are correct.

6. Problem 2: bad ownership or modes for directory /home/tyxk13

6.1 Symptom

The server log shows:

Authentication refused: bad ownership or modes for directory /home/tyxk13

6.2 Cause: StrictModes

OpenSSH's StrictModes defaults to yes, so before accepting a login sshd checks the ownership and permissions of the user's home directory and related files. If the home directory or ~/.ssh is writable by group or others, or the owner is neither the user nor root, authentication is refused.

The security rationale is straightforward: if someone else can write your ~/.ssh/authorized_keys, they can insert their own public key and take over the account.

The most common triggers in real environments:

  • The home directory was set to 775 or 777 for file sharing.
  • The home directory is a Samba/NFS share whose permissions were loosened by the share configuration.
  • Someone ran chown -R as root and changed the home directory owner incorrectly.
  • The user directory was just created and ownership/permissions were never set correctly.

6.3 Diagnose

Check the three permissions on the server in order:

ls -ld /home/tyxk13
ls -ld /home/tyxk13/.ssh
ls -l /home/tyxk13/.ssh/authorized_keys

To inspect the owner and permissions of every level in the path, namei is more intuitive:

namei -l /home/tyxk13/.ssh/authorized_keys

In this session the problem was the /home/tyxk13 home directory itself: it was too permissive or had the wrong owner, so sshd refused at the very first directory check.

6.4 Fix

Run on the Debian server:

# Home directory: must be owned by the user and must not be writable by group or others
sudo chown tyxk13:tyxk13 /home/tyxk13
sudo chmod 755 /home/tyxk13

# .ssh directory and authorized_keys
sudo chown -R tyxk13:tyxk13 /home/tyxk13/.ssh
sudo chmod 700 /home/tyxk13/.ssh
sudo chmod 600 /home/tyxk13/.ssh/authorized_keys

The normal state after the fix:

drwxr-xr-x tyxk13 tyxk13 /home/tyxk13
drwx------ tyxk13 tyxk13 /home/tyxk13/.ssh
-rw------- tyxk13 tyxk13 authorized_keys

The home directory can also be set to 750 (group members can enter) or 700, depending on whether other users genuinely need access; the key requirement is that it must not be writable by group or others.

6.5 Verify

Reconnect from the client:

ssh -i ~/.ssh/id_ed25519 tyxk13@192.168.10.13

If it logs in directly, public key authentication has succeeded. Fixing permissions does not require restarting sshd or regenerating keys.

6.6 Do not work around it by disabling StrictModes

Setting StrictModes to no in sshd_config does make the error disappear, but it also allows others to modify your authorized_keys, which is far riskier than the benefit. The correct approach is to fix directory permissions; if the issue really comes from a Samba share, adjust the share structure or permissions instead of loosening SSH checks.

7. Optional hardening: disable password login

Do this only after key login works completely. Keep one already authenticated SSH session open while making the change, verify with a new connection, and only then close the old session, so you do not lock yourself out.

On Ubuntu/Debian, check /etc/ssh/sshd_config and the files under /etc/ssh/sshd_config.d/ (when the same setting appears multiple times, pay attention to which value takes effect). Make sure the effective values are:

PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no

Then validate and reload:

sudo sshd -t
sudo systemctl reload ssh

reload reloads the configuration without dropping existing sessions and is safer than restart. The service name may be ssh or sshd depending on the distribution; on some systems sshd is not in PATH, so use /usr/sbin/sshd -t. Whether root can log in directly also depends on PermitRootLogin.

8. Multiple servers and multiple keys

One key pair can be reused: append the same public key to ~/.ssh/authorized_keys on every server, then configure different aliases in ~/.ssh/config.

ssh server1
ssh server2

If different environments need different keys (for example, production and testing separated), specify each IdentityFile per Host in the config, and use IdentitiesOnly yes to avoid the client trying every key in the agent one by one.

9. FAQ

Q: Why does it still ask for a password after configuration?

First distinguish which password: Enter passphrase for key is the private key passphrase; tyxk13@192.168.10.13's password: is the server account password. The latter means public key authentication did not succeed. Use ssh -v to see what the server returned after Offering public key.

Q: Do I need to restart sshd after changing authorized_keys?

No. authorized_keys and permissions are read on each authentication, so just reconnect after changing them. Only changes to sshd_config require systemctl reload ssh.

Q: How do I troubleshoot Permission denied (publickey)?

Check in order: whether the public key is installed for the current user, whether the fingerprints match on both sides, the owner and permissions of the home directory, .ssh, and authorized_keys, and the server log.

Q: Can the public key be made public?

Yes. The public key is meant to be handed to servers for verification; only the private key must be kept secret. The private key file should have permissions 600.

Q: What if I have to type the private key passphrase every time?

Cache it with ssh-agent. On Linux/WSL run eval "$(ssh-agent -s)" followed by ssh-add ~/.ssh/id_ed25519; with the Windows OpenSSH client, enable the ssh-agent service and then use ssh-add.

Q: Why can't the home directory be set to 777?

StrictModes considers that others can write the home directory and therefore replace authorized_keys, so it refuses authentication. When file sharing is needed, keep the shared directory separate from the home directory.

10. Summary

The whole chain can be remembered as five steps:

  1. Generate a key pair on the client.
  2. Append the public key to the target user's ~/.ssh/authorized_keys.
  3. Test the login with the specified key.
  4. Add an entry to ~/.ssh/config to simplify connections.
  5. Disable password authentication only after everything is confirmed working.

The troubleshooting order for the two problems in this session is also fixed: first use ssh -v to confirm what the client did, then compare public key fingerprints on both sides, then check the server log with journalctl -u ssh -f, and finally inspect the directory permissions related to StrictModes.

In one sentence: when key login fails, look at the server log and directory permissions first, instead of regenerating keys or editing sshd configuration over and over.
